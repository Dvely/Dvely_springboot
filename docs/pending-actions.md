### 1-0. GitHub App 에서 `checks` 권한 + `check_run` 구독 제거 — **영향 0** (#414)

불필요의 **근거는 코드**이므로 등록과 무관하게 참이다 — `src/main` 에 Checks API 호출 0건이고 `WebhookEventHandler` 에 `check_run` case 가 없다(PR #431).

**단, App 등록은 환경마다 다르다.** 측정된 수치(`GET /app`)는 `dvely-test-app` 것이고 운영 App 은 아직 측정되지 않았다 — dev 와 운영의 공개 OAuth `client_id` 가 다르다(`Ov23lifhsh…` vs `Ov23liHbLL…`). **쓰이는 등록마다** 끄고, 운영 App 에 애초에 `checks` 가 붙어 있는지부터 확인한다.

**권한 제거는 즉시 적용되고 재승인이 필요 없다** — 재승인이 필요한 쪽은 추가다. 공지도 UX 도 필요 없다.

```
GitHub App 설정 → Permissions & events
  Repository permissions → Checks  →  No access
  Subscribe to events    → Check run  →  체크 해제
```

**성공 판정**: `./gradlew test --tests '*GithubAppPermissionProbe*' -Dgithubapp.it=true -i` 를 다시 돌려 `permissions` 에서 `checks` 가, `events` 에서 `check_run` 이 사라진 것을 본다.

### 1-1. Let's Encrypt 인증서 — **완료 (2026-09-25)**

```
issuer=Let's Encrypt CN=YE2 · subject=CN=qeploy.com · 만료 2026-12-24
nginx qeploy.com:443 블록이 /etc/letsencrypt/live/qeploy.com/ 을 쓴다
certbot renew --dry-run  →  성공
deploy hook  /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh  설치
```

**성공 판정**: 검증 켠 상태로 오리진에 HTTPS 가 붙는다(`--resolve` 로 3/3 200). 전에는 `code=000` 이었다.
Cloudflare 경유도 교체 뒤 그대로 정상(5/5).

**이제 가능해진 것**: Cloudflare 가 불안정할 때 **DNS 를 grey cloud 로 돌려 우회**할 수 있다. 전에는
오리진 인증서가 Cloudflare Origin CA 라 그렇게 하면 전 사용자 HTTPS 가 깨졌다. orange cloud 로 두어도
무해하다(Full/strict 가 공개 신뢰 인증서를 그대로 받는다).

**되돌리려면** `ssl_certificate` 두 줄을 `/etc/ssl/cloudflare/dvely-origin.{pem,key}` 로 바꾸면 된다 —
옛 인증서는 지우지 않았다. 백업: `dvely.bak-swap-20260925-202903`.

> **여기서 두 가지를 배웠다.**
>
> **① 장애가 자기 해결책을 막는다.** 첫 발급 시도가 **522** 로 실패했다 — Cloudflare 가 오리진에 닿지
> 못해서, HTTP-01 챌린지도 닿지 못했다. 엣지가 불안정할 때 쓰려고 만드는 우회로를, 바로 그 불안정
> 때문에 만들 수 없었다. 경로가 건강한 창을 확인한 뒤에야 성공했다. **비상 대비는 평시에 해 둬야 한다.**
>
> **② `server` 직속 `return` 은 location 매칭보다 먼저 실행된다.** 80 포트 블록이 이랬는데
> ACME location 을 통째로 삼켰다(평문 HTTP 챌린지가 301). `return` 은 rewrite 단계라 location 선택보다
> 앞선다. `location /` 로 내려야 `^~` 접두사 매칭이 이긴다. **이 수정은 90일마다 도는 자동 갱신에도
> 필요하다** — 안 고쳤으면 갱신이 조용히 실패했을 것이다.
>
> 만료 알림은 받지 않는다(이메일 없이 등록). 필요하면 `certbot update_account -m <메일>`.

### 1-3. 오리진 리전 — 근본 원인

**사용자는 한국인데 오리진이 싱가포르(`13.251.154.173`, ap-southeast-1)다.** 이틀간 관측한 모든
지연·실패가 이 구조에서 나왔다.

```
2026-09-23 아침  HKG  0.120s / NRT 0.223s   정상
2026-09-23 밤    SEA  0.32s
2026-09-24 낮    LAX  평균 1.04s (최대 2.95s)
2026-09-25 아침  ATL  2.80s · 실패율 67%
2026-09-25 낮    SJC  0.35s · 실패율 0%
2026-09-26 00:0x SJC  실패율 55% (20회) → 40% (15회)
```

**사흘 연속이다 — 일시적 사고로 볼 수 없다.** 09-26 측정은 릴리스(PR #394) 직후 헬스 체크가 522(46초)로
떨어져서 원인을 가르려고 **같은 시점에** 두 경로를 나란히 잰 것이다.

```
오리진 직접 (Cloudflare 우회)   15/15 성공 · ~10ms
Cloudflare 경유                  9/15 성공 · colo=SJC
```

배포 탓이 아니다. 같은 순간 `cloudflare.com` 은 ICN(서울)을 주고 오리진 직접은 평평하다 —
**우리 코드도 서버도 아니다.** 서울(`ap-northeast-2`)로 옮기면 엣지가 어디에 붙든 거리가 줄고 ICN 엣지에

### 2-1. `#344` 9-2 — SDK 클라이언트 캐시 (과금 아님)

**#344 의 과금 항목(9-3 ECR · 9-4 EIP)은 끝났다.** 남은 9-2 는 지연·커넥션 설정이다.

제안은 "연결별 클라이언트 캐시 + 잦은 경로는 `ApacheHttpClient`" 인데, **클라이언트만 캐시하면 얻는
것이 거의 없다** — 현재 `UrlConnectionHttpClient` 는 커넥션 풀이 없어서 객체를 재사용해도 요청마다
TCP+TLS 를 새로 맺는다. 실제 비용은 그쪽이고 클라이언트 생성(로컬 작업)은 아니다.

값을 내려면:
- `apache-client` 는 **선언된 의존성이 아니다**(`build.gradle` 에 `url-connection-client` 만) — 추가 필요
- `UrlConnectionHttpClient` 가 **12개 클래스**에 퍼져 있다
- 클라이언트를 캐시하면 수명 관리가 따라온다(9-1 이 provider 하나에 대해 한 것을 다섯 종류에)

## 4. FE 쪽 (`Dvely_FE`) — 참고

> **용어 합의 (2026-09-30).** "dev" 는 **BE dev 박스(`54.251.165.129`)** 를 뜻한다. FE 세션의 맥북 로컬 Vite(`localhost:5173`)는 **"로컬 vite"** 로 부른다. 같은 단어가 두 기계를 가리켜 BE 쪽에서 엉뚱한 박스의 `dmesg`·JVM 힙을 훑은 일이 있었다 — 로컬 vite 가 하네스 메모리 부족으로 kill 된 것이었고 BE dev 는 멀쩡했다.

FE 는 `main` 하나가 통합 브랜치이고 **머지가 곧 프로덕션 배포**다(BE 와 모델이 다르다).

`#106`(SSE 커서) `#107`(뒤로가기 캐시) `#108`(복원 시 진행 표시) `#110`(가짜 크레딧)
`#111`(조각 로딩 실패) `#112`(lint 차단) 에 이어, 2026-09-26 에 **갤러리가 프로덕션에 나갔다**.

| PR | 내용 |
|---|---|
| `#115` (`da1ac96`) | 홈 탐색·생성 미리보기·프롬프트 얹기가 서버 카탈로그를 본다 |
| `#117` (`41a20f3`) | 랜딩 `/` 과 갤러리 `/template` 도 — **더미 목록 제거 완료** |
| `#118` | 카탈로그 실패 시 다섯 화면의 메시지 수정 + 재시도 버튼 |

`#118` 이 고친 것이 특히 중요하다. 카탈로그가 실패하면 다섯 화면이 **거짓말을 하고 있었다** —
`/project/new` 는 멀쩡히 있는 템플릿을 "주소가 바뀌었거나 더 이상 제공되지 않는 템플릿입니다"라고
**단언해서** 사용자를 돌려보냈고, 랜딩은 필터가 "모든 업종"인데 "해당 업종의 템플릿을 준비 중"이라고
했다. 503 이 몇 초짜리여도 그 몇 초에 들어온 사람은 "이 템플릿 없어졌구나" 하고 나간다.

FE 확인 결과 **통째로 빈 화면이 되는 곳은 없고 랜딩은 섹션만 빈다.**

**갤러리 착수에 필요한 BE 계약은 다 답해 뒀다:**

- 씨딩은 **첫 CODE 스텝**에서 돈다(`CodeAgentService:199`). 생성 시점엔 검증+저장만 한다
- 그래도 **`templateType` 은 생성 요청에만 실을 수 있다** — 수정 경로는 그 필드를 받지 않는다.
  생성 후에 붙일 방법이 없으므로 템플릿 선택이 `POST /projects` 에 도달해야 한다
- **`startMode: 'template'` 과 `templateType` 을 반드시 같이** 보내야 한다. `startMode: 'blank'` 이면
  `normalizeTemplateType` 이 `templateType` 을 **조용히 null 로 버린다**(오류도 없다)
- 없는 `templateType` 은 **400**(`TemplateCatalogGuard`). 카탈로그 id 만 보내야 한다
- `thumbnailUrl` 은 **nullable** 이다 — 카탈로그를 Pages 에서 실시간으로 받으므로 발행 순서에 따라
  없을 수 있다. FE 는 없으면 텍스트 카드로 떨어지게 만들기로 했다
